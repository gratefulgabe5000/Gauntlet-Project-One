**Date**: October 19, 2025  
**Status**: Investigating Root Cause

## 📊 **What We Know**

### **Performance Baseline**
| State | FPS | Render Time | Status |
|-------|-----|-------------|--------|
| **Idle** | 60-61 | 16.6ms | ✅ Perfect |

| Attempt | FPS Result | Change | Conclusion |

### **Key Findings**

1. ✅ **Idle performance is perfect** (60 FPS) - no inherent rendering issues
2. ❌ **Multi-select triggers massive re-renders** - 14-24 FPS (vs 60 FPS target)
3. ❌ **useCallback made it WORSE** - suggests we're not addressing root cause
4. ✅ **React.memo() is working** - proved by the 13 → 24 FPS improvement
5. ⚠️ **useMemo not working as expected** - callbacks still changing somehow

## 🤔 **Hypotheses**

### **Hypothesis 1: Parent Re-renders on Every Selection**
**Theory**: App.tsx re-renders whenever `selectedShapeIds` changes, recreating all callbacks, breaking Canvas's useMemo.

**Evidence**:
- useMemo dependencies include callbacks from App.tsx
- If App re-renders, callbacks get new references
- useMemo sees "changed" dependencies → recreates all shapes
- React.memo() can't prevent re-renders (shape elements are new)

**How to Test**:
- Add console.log to App.tsx to count renders
- Check if App renders on every selection change

---

### **Hypothesis 2: Set State Updates Are Inefficient**
**Theory**: Updating a `Set` via `setSelectedShapeIds` might be triggering more re-renders than expected.

**Evidence**:
- We create a `new Set(prev)` on every selection change
- Even if content is the same, Set reference always changes
- This could trigger unnecessary re-renders

**How to Test**:
- Log when `selectedShapeIds` changes
- Check if Set updates are batched or happen multiple times

---

### **Hypothesis 3: Shapes Array Reference Changes**
**Theory**: The `shapes` array from useShapes might be getting a new reference on selection changes (even though data hasn't changed).

**Evidence**:
- useMemo depends on `shapes`
- If `shapes` reference changes, all shapes recreate
- This would explain why ALL shapes re-render, not just selected ones

**How to Test**:
- Log when `shapes` reference changes
- Check if Firestore subscription updates `shapes` unnecessarily

---

### **Hypothesis 4: Konva Layer Re-rendering**
**Theory**: The entire Konva `<Layer>` might be re-rendering, forcing all shapes to re-render regardless of memoization.

**Evidence**:
- Konva's rendering is managed by react-konva
- Layer re-renders might bypass React.memo()

**How to Test**:
- Add console.log to Layer component
- Check if Layer re-renders on selection

## 🎯 **Investigation Steps**

### **Step 1: Add Render Logging** (5 min)
Add console.log statements to track renders:

```typescript
// In App.tsx
console.log('🔄 App rendered', { selectedCount: selectedShapeIds.size });

// In Canvas.tsx (inside component)
console.log('🎨 Canvas rendered', { shapeCount: shapes.length });

// In Canvas.tsx (inside useMemo)

// In shape components (Rectangle, Circle, etc.)

```

**Expected Result**: Identify which components are re-rendering and when.

---

### **Step 2: Profile with React DevTools** (10 min)
Use React DevTools Profiler to record a multi-select operation:

1. Open React DevTools → Profiler tab
2. Click "Record"
3. Multi-select 10 shapes (Shift+Click)
4. Stop recording
5. Analyze which components re-rendered

**Expected Result**: Visual proof of which components are causing re-renders.

---

### **Step 3: Test Shape Memoization** (5 min)
Add a counter to shape components to verify React.memo() is working:

```typescript
let renderCount = 0;

const Rectangle = React.memo(({ shape, isSelected, ...props }) => {
  renderCount++;
  console.log(`🔷 Rectangle ${shape.id} render #${renderCount}`, { isSelected });
  // ... rest of component
});
```

**Expected Result**: If memoization works, render count should only increment for shapes whose `isSelected` changes.

---

### **Step 4: Test Shapes Reference Stability** (5 min)
Track if the `shapes` array reference changes:

```typescript
const prevShapesRef = useRef(shapes);

useEffect(() => {
  if (prevShapesRef.current !== shapes) {
    console.log('⚠️ Shapes reference CHANGED (even though data might be same)');
    prevShapesRef.current = shapes;
  }
}, [shapes]);
```

**Expected Result**: Identify if `shapes` is getting new references unnecessarily.

---

### **Step 5: Test App.tsx Re-renders** (5 min)
Count how often App.tsx re-renders:

```typescript
const renderCountRef = useRef(0);

useEffect(() => {
  renderCountRef.current++;
  console.log(`🏠 App render #${renderCountRef.current}`, {
    shapesCount: shapes.length,

  });

```

**Expected Result**: Determine if App re-renders on every selection change.

## 🛠️ **Potential Fixes** (Based on Investigation Results)

### **Fix 1: Prevent App Re-renders**
If App is re-rendering unnecessarily:
- Move selection state down to Canvas component
- Use Context for shared state
- Optimize state updates to reduce re-renders

---

### **Fix 2: Stabilize Shapes Array**
If `shapes` reference changes unnecessarily:
- Memoize `shapes` in useShapes hook
- Only update reference when actual shape data changes
- Use structural equality check instead of reference equality

---

### **Fix 3: Optimize Konva Rendering**
If Konva Layer is the issue:
- Split shapes into multiple layers (selected vs unselected)
- Use Konva's built-in optimization features
- Consider using `FastLayer` for better performance

---

### **Fix 4: Batch State Updates**
If multiple state updates are happening:
- Use `unstable_batchedUpdates` from React
- Consolidate state updates into single setState call
- Use reducer pattern to batch related updates

## 🎓 **Lessons Learned**

1. **Don't guess - profile first**: The useCallback attempt made things worse because we didn't identify the real issue first.
2. **Regressions are data**: The 42% FPS regression tells us our theory was wrong.
3. **Memoization is a chain**: If any link breaks (App → Canvas → Shapes), the whole optimization fails.
4. **React DevTools Profiler is essential**: Visual profiling is faster than guessing.
