# ❌ useCallback Regression Analysis & Fix

**Date**: October 19, 2025  
**Phase**: Phase 4a - Block 4 (Performance Optimization)  
**Issue**: useCallback made performance WORSE (33 FPS → 12 FPS)

---

## 📊 **Performance Results**

| Scenario | Before useCallback | With useCallback | Change |
|----------|-------------------|------------------|---------|
| **Idle** | 60 FPS | 60 FPS | ✅ No change |
| **Create 20 circles** | ~53 FPS | 52 FPS | ✅ No change |
| **Multi-select** | 33 FPS | **12 FPS** | ❌ **-63%!** |

---

## 🔍 **Root Cause Analysis**

### **The Problem:**
We wrapped callbacks in `useCallback` with dependencies like `showError`, `showSuccess`, `updateShapeText`, etc.:

```typescript
const handleColorChange = useCallback(async (shapeId: string, color: string) => {
  // ...
}, [updateShapeColor, showSuccess, showError])
    ↑                      ↑              ↑
    These dependencies are NOT stable!
```

### **Why It Failed:**
1. **Dependencies are recreated on every render:**
   - `updateShapeColor` from `useShapes` hook
   - `showError`/`showSuccess` from `useToast` hook
   - These hooks don't use `useCallback` internally

2. **useCallback added overhead without benefit:**
   - React checks if dependencies changed → **They did (every render!)**
   - React creates a new callback anyway
   - **But** the `useCallback` wrapper adds extra overhead
   - **Result**: Slower than before!

3. **The useMemo was working correctly:**
   - Console logs confirmed `useMemo` only re-ran when selection changed ✅
   - But the callbacks were still unstable, causing Canvas re-renders

### **Secondary Problem: Presence Heartbeat**

The logs revealed a **second critical issue**:

```
👥 Visible users: 1
🎨 Current user color updated: #98D8C8  ← EVERY heartbeat (5 sec)
👤 Current user name updated: User      ← EVERY heartbeat (5 sec)
🏠 App render #39
```

**Why?** The `usePresence` hook had a **stale closure bug**:

```typescript
// OLD CODE (BUGGY):
const unsubscribe = subscribeToPresence((users) => {
  if (currentUser.cursorColor !== currentUserColor) {  // ❌ Stale value!
    setCurrentUserColor(currentUser.cursorColor);
  }
});
}, [user]);  // ← Missing currentUserColor dependency!
```

The `currentUserColor` variable was stale inside the callback, so the comparison always failed, triggering `setState` on **every presence update** (including the 5-second heartbeat).

---

## ✅ **The Fix**

### **1. Reverted useCallback in App.tsx**
```typescript
// Removed all useCallback wrappers from:
// - handleTextChange
// - handleColorChange  
// - handleFontSizeChange
// - handleZoomIn
// - handleZoomOut
```

### **2. Fixed Stale Closure in usePresence.ts**
```typescript
// PR10a: Use refs to prevent stale closures
const currentUserColorRef = useRef<string>(currentUserColor);
const currentUserNameRef = useRef<string>(currentUserName);

// Update refs when state changes
useEffect(() => {
  currentUserColorRef.current = currentUserColor;
  currentUserNameRef.current = currentUserName;
}, [currentUserColor, currentUserName]);

// Use refs in subscription callback
const unsubscribe = subscribeToPresence((users) => {
  if (currentUser.cursorColor !== currentUserColorRef.current) {  // ✅ Fresh value!
    setCurrentUserColor(currentUser.cursorColor);
    currentUserColorRef.current = currentUser.cursorColor;
  }
});
```

## 📝 **Key Learnings**

1. **`useCallback` is not a magic fix**
   - Only helps if dependencies are stable
   - Can make things worse if dependencies change frequently

2. **Stale closures are subtle bugs**
   - Missing dependencies in effect arrays cause stale values
   - Use refs when you need fresh values but don't want to trigger re-renders

3. **Measure before optimizing**
   - The render logging was CRITICAL to finding these issues
   - Without logs, we'd be guessing

4. **Multiple issues can compound**
   - Presence heartbeat bug + useMemo dependencies + useCallback overhead
   - Each made the others worse
